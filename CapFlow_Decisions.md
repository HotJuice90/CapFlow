## Расчётное ядро

### 1. Налог — настраиваемый
Ставка налога и необлагаемый лимит задаются пользователем в настройках.
Движок применяет их к **годовому кумулятивному** процентному доходу по **всем**
активам (как точный НК РФ по структуре, но числа берутся из настроек, а не зашиты).
Фиксация налога — по итогам года (на 31 декабря) и в момент закрытия актива (Snapshot).

**Уточнения, появившиеся позже:**
- **Лимит по закону**: по умолчанию — 1 млн × максимальная ключевая ставка года
  (берётся с 1-го числа каждого месяца). Пока `taxFreeLimitManual` не включён, значение
  не замораживается в настройках, а выводится из истории ставки — иначе молча устаревало
  при каждой смене ставки ЦБ. Ручное значение — только при включённом флаге.
- **Кто платит** (`Asset.taxWithheldByBank`): если налог удерживает площадка
  (брокер, ЦФА-обёртка), это не проценты по вкладу в смысле ст. 214.2 НК — лимит на такой
  доход не распространяется вообще: он ни занимает лимит, ни пользуется им. Признак
  живёт на АКТИВЕ, а не на типе инструмента: по типу не угадывается («МТС накопления»
  выглядят как накопительный счёт, внутри — брокерский инструмент).
- **2021–2022** — проценты по вкладам и счетам не облагались (67-ФЗ от 26.03.2022).
  Миграция обнуляет `taxToPaySelf` в уже зафиксированных записях за эти годы.

### 2. «Доход в день» — мгновенный
Единый KPI во всём приложении:

```
доход_в_день = текущая_сумма × ставка / дней_в_году
```

- День-каунт: `actual/365-366` (делим на реальное число дней в текущем году).
- Для накопительного счёта — капает на текущий остаток (как МТС/Яндекс Сейв).
- Для вклада без капы — постоянное число весь срок (мгновенный = усреднённый).
- Для вклада с капой — растёт по мере роста базы.

На главной и в аналитике «доход в день» = сумма по всем активам.

### 3. Капитализация — простой % по умолчанию + опция
- По умолчанию актив считается **простым процентом** (без капитализации).
- Капитализация — опциональный флаг + период (ежемес/ежекв/…). При включении движок
  капитализирует начисленные проценты в базу в дату выплаты.
- Режим «выплата процентов на сторону» в MVP фиксируется как `получено N` в истории
  актива (часть «уже заработано»), но **не копится** в отдельный баланс
  (свободный капитал вне MVP).

**Обновлено:** второй пункт больше не верен. Выплаты теперь бывают двух видов —
`PayoutRecord.action = 'keep' | 'wallet'` (`src/domain/types.ts`): «оставить» причисляется
к телу и работает дальше, «в кошелёк» уходит в свободный капитал (см. #4) и фиксируется
суммой. Выбор делается в шите `app/payout.tsx` на каждую выплату; записи нет = «оставить».
Отсчёт правила — с `Asset.payoutsSince`, чтобы появление механики не пересчитало историю
задним числом. Появление этого механизма также закрыло частую ошибку «тело худеет
на сумму процентов»: у снятий есть `BalanceAdjustment.kind = 'body' | 'interest'`.

### 4. Свободный капитал — РЕАЛИЗОВАНО (исходное решение отменено)
Изначально: «убрать с главной и из аналитики, остаётся только работающий капитал,
вернуть вместе с поведением „Денежный“ после MVP».

**Сейчас (обновлено 19.11.2026)** — свободный капитал есть в продукте и в коде:
- Это **лента движений** `FreeCapitalEntry` (`src/domain/types.ts`): дата, сумма,
  валюта, комментарий. **Сумма — ДЕЛЬТА** (+ пополнение, − списание), в отличие от
  `BalanceAdjustment` по активу, где хранится абсолютный баланс. Баланс свободных
  денег = сумма записей (`freeCapitalBalance` в selectors), а не разница с общим тоталом.
- Мутации — `src/state/actions/useFreeCapitalActions.ts` (`add` / `update` / `delete`).
- UI — саб-экран Настройки → «Капитал» (`app/settings/capital.tsx`): баланс, его доля
  в общем капитале, добавление/удаление записей свайпом, форма с датой и комментарием.
- Деньги вне активов показываются рядом с работающим капиталом (hero главной
  получает `freeCapital` отдельно от `workingCapital`, в аналитике — своя карточка).

**Что этим НЕ сделано:** «псевдосчёт» — воображаемый доход на свободные деньги
(по какой ставке их можно было бы разместить). Не реализовано, смысл нужно обсудить
заново. Прошлый хак `settings.manualTotalCapital` (одно вручную перепечатываемое
число) остался только для чтения старых сохранений — поля не пишутся и не читаются новым UI.

## Внешние данные

### 5. Курсы валют — API ЦБ РФ
Источник cbr.ru (бесплатный, официальный, раз в день, без ключей).
Офлайн — последний успешно полученный курс. Показываем источник + дату обновления.

**Уточнено:** фактически тянем с **cbr-xml-daily.ru** (зеркало фида ЦБ), см.
`src/rates/cbr.ts`. Список валют — 10: RUB, USD, EUR, TRY, KZT, BYN, CNY, INR, AED, BRL
(порядок из Figma). ARS убран: ЦБ его не публикует вообще, ни текущим значением, ни
историей. Ручной override (`manualRates`) приоритетнее автокурса, при этом `rates`
продолжает обновляться в фоне — чтобы рядом с ручным значением можно было показать курс ЦБ.

### 6. Ключевая ставка ЦБ — авто из API ЦБ
Тянется автоматически (вместе с курсами). Нужна для «премии к ключевой» и налогового
лимита. Офлайн — последнее сохранённое значение.

**Уточнено:** хранится как **история точек** изменений (`keyRateHistory`), а не одно число:
налоговый лимит считается от максимума года, а история — редко меняющееся и не переписываемое
задним числом, поэтому при обновлении домердживаем свежие записи, а не тянем всё заново.
Сверка с ЦБ идёт раз в 7 дней (ставка меняется раз в недели, но «действует с июня» без
сверки неотличимо от «мы с июня не смотрели»); сами курсы — раз в ~22 часа.

### 7. Защита входа — нет в MVP
Биометрия/PIN не входят в первую версию. **Архитектурно** оставить место под
экран-замок (gate на старте навигации), чтобы вкрутить `expo-local-authentication`
позже без переписывания.

## История и аналитика

### 8. Snapshot — в обоих сценариях
И «Закрыть», и «Архивировать» создают Snapshot (фиксация итоговых цифр + версия
движка). **Но**: архивные снапшоты помечаются флагом `excludeFromAnalytics = true` —
доступны в истории, но не участвуют в расчётах доходности (архив = ошибочные/
неактуальные записи).

**Уточнено:** вместе со снапшотом спрашивается **фактическая дата закрытия**
(`Asset.closedDate`, через date-picker), а не берётся момент нажатия кнопки: закрыл 1-го,
отметил 4-го — без даты история капитала завышалась на все дни между. Старые записи поля
не имеют — там откат на дату снапшота. Ещё есть понятие «просрочен истёк в ПРОШЛОМ году»
(`isPastYearMatured`): такой актив на текущих экранах не показывается вообще, только
в истории/архиве; в ТЕКУЩЕМ году просроченный живёт как обычно, с пометкой «нужно решение».

### 9. График капитала — реконструкция из первичных данных
История капитала строится задним числом из активов и их дат (открытие/закрытие/
пополнения), а не из ежедневных снимков. Ложится на принцип «храним только первичные
данные». Минус принят: редактирование актива задним числом перерисовывает прошлое.

### 10. Инсайты — 2-3 базовых правила
Детерминированные правила в MVP:
- «Скоро заканчивается крупный вклад» (срочные, осталось ≤ N дней).
- «Средняя ставка портфеля выше/ниже ключевой».
- (резерв) «Часть капитала освобождается в этом месяце».
Без сложного движка приоритизации — добавим позже.

### 11. Объясняющая аналитика + сравнение периодов — базово в MVP
Простые сравнения (сегодня↔вчера, месяц↔месяц) + объяснение по 1-2 значимым событиям.
**Архитектуру событий закладываем сразу** (создание/открытие/пополнение/закрытие/…),
даже если полный журнал — после MVP.

## Платформа и техстек

### 12. Платформа — Android-first
Основной фокус Android (iOS следом). Дизайн-гайд уже учитывает Android-грабли
(blur, шрифты, тени через `boxShadow`).

**Уточнено по факту сборки:** iOS-сборка не ведётся, `ios.bundleIdentifier` в `app.json`
заполнен «на будущее». Живая схема релиза — полный APK через **GitHub Releases**
(`HotJuice90/CapFlow`) + системный установщик в самом приложении: скачивание в кэш,
`content://` через `FileSystem.getContentUriAsync`, разрешение `REQUEST_INSTALL_PACKAGES`.
`expo-updates` сознательно НЕ используется (магазинный движок обновлений сделает это лучше;
решение принято, не пересматривать). APK ≈ 44 МБ — собран только под `arm64-v8a`.

### 13. Язык — русский, i18n-ready
UI на русском, строки вынесены в словарь, чтобы добавить языки позже без переписывания.

### 14. Хранилище — AsyncStorage за слоем repository
AsyncStorage для MVP, но **строго за абстракцией `repository`**. Миграция на
`expo-sqlite` при росте (история событий, сотни активов) — без боли.

**Сделано:** `src/storage/repository.ts` (сохранение/загрузка, бэкап, аварийный ключ),
`src/storage/types.ts` (`AppData`, `SCHEMA_VERSION = 1`, дефолты), `src/storage/migrate.ts` —
единственное место, где старые сохранения приводятся к текущей форме. Формально версия схемы
не бампалась ни разу: все изменения полей добираются миграцией «на месте» (бэкафилл +
одноразовые пересчёты со своими маркерами вроде `Asset.payoutsSince`).

### 15. Первый запуск — демо-данные + сброс (обновлено)
На первом запуске наполняем приложение **демо-портфелем** (помечен `isDemo`), чтобы
срез читался на живых цифрах. В настройках — кнопка **«Удалить тестовые данные»**
(чистит только `isDemo`-записи). Пустые состояния по гайду (карточка + иконка +
подсказка + CTA) всё равно реализуем — они показываются после удаления демо.

## План сборки

### 16. Подход — вертикальный срез
Сначала одна сквозная фича целиком, потом расширяем вширь.

**Срез 1 (первый рабочий результат):**
1. Расчётный движок (чистый TS-модуль, без RN) + юнит-тесты — вклад (Срочный).
2. Минимальный справочник организаций (для создания актива).
3. Создание актива «Вклад» с живым предрасчётом.
4. Главная: доход в день (сумма) + работающий капитал + список активов.
5. Карточка вклада: Hero (доход/день, ставка, сумма, бейдж «осталось N дней») +
   финансовый результат (начислено/налог/чистыми) + второй блок (срок/прогресс).

Дальше: накопительный счёт (Бессрочный) → аналитика → календарь → конвертер → настройки.

### 17. Набор инструментов MVP
- **Вклад** (поведение: Срочный)
- **Накопительный счёт** (поведение: Бессрочный)
- **ЦФА — после MVP** (логика = вклад, добавится как тип над «Срочным»).

**Обновлено:** в типе `InstrumentTypeId` сейчас четыре значения — `deposit`, `savings`,
`bond`, `dfa`. Облигации с фиксированным купоном добавлены как полноценный тип (они
соответствуют «философии» — доход предсказуем наперёд), ЦФА тоже уже в типе, хотя
отдельного «режима» под них не выделяли. Новые типы добавлять только с предсказуемой ставкой:
акции, фонды, ETF, флоатеры и структурные продукты — нет.

## Инженерные принципы (зафиксировано)

- **Расчётный движок — отдельный чистый модуль** `calc/` без зависимостей от RN:
  `calculate(asset, params, now) → derived`. Покрыт юнит-тестами. Единый источник
  истины для главной/аналитики/календаря/карточек.
  **Важно:** `calculate` проходит ВСЮ жизнь актива и в цикле по дням даёт квадрат — для рядов
  есть `accrualSeries(asset, instrument, dates)`, один проход с выборкой во всех датах сразу.
  Внутри движка всё в числовых индексах дней, а не ISO-строках. Версия движка пишется в
  снапшоты (`ENGINE_VERSION`).
- **Хранятся только первичные данные.** Все производные — на лету (по спеке). Кроме явных
  исторических фактов: снапшоты и зафиксированные года (`TaxYearRecord`).
- **День-каунт** везде `actual/365-366`.
- **Денежный формат** — российский: пробел-разделитель тысяч, символ валюты после
  числа через пробел (по спеке).
